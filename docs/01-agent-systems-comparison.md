# Agent 系统对比：OpenCode vs Hermes vs OpenClaw

## 摘要

本文档对三个主流开源 AI 编码 Agent 系统进行对比分析，为手机客户端桥接的架构设计提供依据。目标是找出通用模式和各系统的独特能力，确定手机客户端需支持的功能范围。

---

## 1. 系统概览

| 方面 | OpenCode | Hermes Agent | OpenClaw |
|------|----------|--------------|----------|
| **主要用途** | 终端优先编码 Agent | 多模态 AI 助手 | 多通道 AI Agent 网关 |
| **许可证** | MIT | 开源 | MIT |
| **GitHub Stars** | 121K+ | 191K+ | 快速增长中 |
| **核心语言** | TypeScript/Bun | Python + TypeScript (TUI) | Node.js/TypeScript |
| **运行时** | Bun | Python + Node.js | Node.js 22+ |
| **架构** | 客户端/服务器 | 客户端/服务器 + CLI | 网关/插件 |

**核心特性：**
- **客户端/服务器分离**: Hono HTTP 服务器暴露 REST + SSE 端点
- **TUI 框架**: 基于 `@opentui/solid`（SolidJS 终端 UI 框架），非 React/Ink
- **提供商无关**: 通过 models.dev 注册表支持 75+ LLM 提供商
- **MCP 协议**: 一流的模型上下文协议支持
- **LSP 集成**: 内置语言服务器协议客户端
- **事件总线**: 模块间松耦合

## 3. 通信协议

| 协议 | OpenCode | Hermes | OpenClaw |
|------|----------|--------|----------|
| **主要传输** | HTTP + SSE | JSON-RPC over stdio | WebSocket + HTTP |
| **流式传输** | 服务器推送事件(SSE) | 换行分隔 JSON | WebSocket |
| **认证** | Basic + OAuth | API Key | OAuth + API Key |
| **实时更新** | SSE 带心跳 | 事件循环 | WebSocket |

### 协议细节

**OpenCode:**
- REST 端点用于操作
- SSE 用于实时流式传输
- SSE 10 秒心跳

**Hermes:**
- TUI 通过 stdio 启动 Python 网关
- 换行分隔 JSON-RPC
- 基于事件的状态更新

**OpenClaw:**
- WebSocket 用于双向通信
- HTTP 用于 REST 操作
- 通道特定适配器

## 7. 手机客户端设计关键洞察

### 7.1 需采用的通用模式

1. **客户端/服务器架构**: 三个系统都将 UI 与核心逻辑分离
2. **事件驱动更新**: SSE 或 WebSocket 用于实时流式传输
3. **会话持久化**: SQLite 或基于文件的会话存储
4. **工具注册表**: 带权限的集中式工具管理
5. **提供商抽象**: 支持多个 LLM 提供商

### 7.2 移动端特有考量

1. **带宽效率**: 为移动网络压缩流式传输数据
2. **离线支持**: 缓存会话和工具供离线使用
3. **电池优化**: 最小化后台处理
4. **触控界面**: 大触摸目标，手势支持
5. **屏幕空间**: 手机/平板自适应布局

### 7.3 需考虑的特色功能

1. **OpenCode 的 MCP 集成**: 通过外部服务器扩展工具
2. **Hermes 的非阻塞输入**: Agent 处理时可继续输入
3. **OpenClaw 的多通道**: 桥接到消息平台

## 8. 建议

### 8.1 架构选择

**推荐：HTTP + SSE（OpenCode 模式）**

理由：
- 完善的协议，广泛的客户端支持
- SSE 提供高效的服务器推送，无需 WebSocket 的复杂度
- REST 端点操作简单直接
- 与现有 OpenCode 生态兼容

### 8.2 功能优先级

**Phase 1 (MVP)：**
- 带流式传输的聊天界面
- 基本文件操作（read, write, edit）
- 会话管理
- 连接 OpenCode 服务器

**Phase 2：**
- 工具执行（bash, grep, glob）
- MCP 服务器集成
- Markdown/HTML 渲染
- 文件浏览器

**Phase 3：**
- 多服务器支持
- 离线缓存
- 媒体处理
- 语音输入

### 8.3 技术栈

**手机客户端：**
- 框架：React Native + ArkUI（鸿蒙）
- 状态管理：Zustand
- HTTP 客户端：Axios
- Markdown：react-native-markdown

**Bridge 服务器：**
- 运行时：Node.js 或 Bun
- HTTP 框架：Express 或 Fastify
- 数据库：SQLite via better-sqlite3
- WebSocket：ws 或 Socket.IO

## 9. 结论

三个 Agent 系统共享共同的架构模式，验证了我们的方法：
- 客户端/服务器分离提供灵活性
- 事件驱动流式传输确保响应性
- 可扩展工具系统提供能力
- 会话管理确保连续性

我们的手机客户端应采用这些经过验证的模式，同时针对移动端限制（带宽、电池、触控）进行优化。HTTP + SSE 协议选择提供了功能性和兼容性的最佳平衡。
